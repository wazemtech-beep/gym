## Read caching and announcement layout (2026-10-07)

Shared browser read caching is connected to 73 client files, with read invalidation subscriptions on 40 screens. Fresh JSON reads use bounded memory caches; simultaneous requests share a response, and a second tab can request a cached response over BroadcastChannel after establishing the current server revision. Cache scope includes a digest of session, user, role and permission grants. Auth, file delivery, downloads and operational endpoints are excluded. Explicit refresh bypasses both data caches. Logout/account changes clear browser data. JSON-only storage preserves binary downloads.

127 API route files use a shared wrapper. Data cache hits still authenticate the request. The verified session is reused only for that request. Successful writes invalidate server data and atomically replace a non-sensitive filesystem revision marker after the handler returns. Server-rendered page queries use short, revision-keyed snapshots (14 queries). Open browsers receive revision changes through an authenticated SSE connection and refresh data without discarding their entire component tree. The worker invalidates after every batch, including partially successful batches. Cache filling checks revision/generation so an old request cannot repopulate an invalidated cache. Financial and dynamic reads expire after 15 seconds, other reads after 30 seconds, and relatively stable settings after 120 seconds.

This implementation targets the existing Node deployment on one host. The web server and worker must share the same writable `GYM_CACHE_REVISION_DIR` (default `.gym-cache` under their working directory). Separate deployment hosts need a shared revision backend/volume before using this scheme across them. The revision marker contains no gym records. Unavailable revision storage disables caching on the affected process. Direct/manual database edits are not observable by this marker; short expiries limit retention, but instantaneous manual-DB invalidation requires a database change feed. HTTP/session verification requests still occur; caching does not remove authorization checks. No tests, builds, browser verification, database migrations, or workers were run.

The header announcement manager now renders through a portal with a fixed overlay, contained scrolling, responsive tabs/fields, keyboard focus trapping and body scroll locking.

One SSE connection per browser session is elected with Web Locks where supported; other tabs share revision messages. The offline workout replay effect is independent of cache invalidation, preventing save/replay loops. Unsaved profile edits and notification preferences are preserved during background updates.
