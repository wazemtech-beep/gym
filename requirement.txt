1. Account kaun banayega?
Public signup se koi bhi admin ya trainer nahi ban sakega.
Account        Kaise banega?
Owner        Initial setup ke waqt ek baar owner account create hoga
Receptionist        Owner staff section se account create/invite karega
Trainer        Owner staff section se account create/invite karega
Member        Staff member register karega; uske baad member ka login activate hoga




Member ka gym record aur login account separate honge. App use na karne wale member ka record bhi fees system mein rahega.
2. Owner ka pehla login
Initial setup ka flow:
1. Backend deploy karte waqt secure setup command se owner ka email aur initial password set karenge.
2. Password ka hash database mein save hoga.
3. Owner login karega.
4. First login par initial password change karega.
5. Owner gym details configure karega.
6. Uske baad staff accounts create kar sakega.
Setup dobara run karke doosra owner create nahi hona chahiye. Owner account create karne ka public endpoint nahi rakhenge.
3. Staff account create karne ka flow
Owner → Staff → Add Staff → details + role → invitation → password set → login.
Example: owner receptionist add karega:
Field        Example
Name        Ali
Email        ali@example.com
Role        Receptionist
Status        Invitation pending




Phir:
1. Backend owner ki permission verify karega.
2. Pending account create hoga.
3. Limited-time, single-use activation link generate hoga.
4. Tumhara custom email backend Google SMTP se branded invitation bhejega.
5. Ali link open karke apna password set karega.
6. Account active ho jayega.
7. Login ke baad receptionist dashboard khulega.
Expired invitation ko owner resend kar sakega; purana link invalid ho jayega. Email delivery fail ho toh owner retry kar sakega.
4. Member account activate karne ka flow
Staff member register kare → “Activate app access” → activation → password set → member login.
Do cases rakhenge:
Member ki situation        Activation
Email available hai        Email par activation link
Email nahi hai        Reception par identity verify karke staff limited-time, single-use activation code issue kare




Email na hone par member Member ID + password se login karega. Activation code identity verify karne ke baad member ko diya jayega.
Member khud activation mein role select nahi karega. Backend account ko uske existing member record se link karke Member role assign karega.
5. Normal login ka actual flow
Web aur Flutter mein same backend authentication use hogi:
1. User email ya Member ID + password enter karega.
2. App login request backend ko bhejegi.
3. Backend account find karega aur password verify karega.
4. Account active hai ya suspended, yeh check hoga.
5. Successful login par session create hoga.
6. Backend user ki identity, role aur permissions return karega.
7. App correct dashboard open karegi.
Role        Login ke baad
Owner        Owner dashboard
Receptionist        Reception dashboard
Trainer        Assigned members dashboard
Member        Personal dashboard




Wrong credentials par generic message hoga: “Login details incorrect hain.” Repeated failed attempts par temporary rate limit lagegi.
6. Login yaad kaise rahega?
Better Auth se passwords aur sessions manage karenge; custom email templates/sending tumhare backend mein honge.
Platform        Session handling
Next.js web panels        Secure, HttpOnly cookie; browser requests ke saath session bhejega
Flutter        Auth integration ke mutabiq session credential device ke secure storage mein; API requests ke saath bhejega
Backend        Har protected request par session validity aur current permissions check karega




Session expire ya revoke ho jaye toh app dobara login karwayegi. Logout par backend session invalidate karega aur device/browser se credential remove hoga.

Valid session? → Action allowed? → Is specific record ka access allowed?

8. Password bhool jaye toh?
Situation        Flow
Email wala account        Forgot password → custom email link → new password
Email ke baghair member        Reception par identity verify → staff reset code issue → member new password set kare




Reset links/codes limited-time aur single-use honge. Password reset hone par purane sessions revoke karenge. Staff member ka current password dekh nahi sakega.
9. Role change, suspension aur membership expiry
Event        System ka behavior
Owner staff ka role change kare        Permissions update; existing sessions revoke; next login par naya access
Staff gym chhor de        Account suspend; sessions revoke
Member login suspend ho        Login/API access band; financial history preserve
Membership expire ho        Member login kar sake; expiry, dues aur receipts dekh sake
User logout kare        Current session end
“Logout all devices” kare        Us account ke saare sessions end




Membership expiry aur login suspension alag cheezein hain. Expired membership wale member ko renewal aur payment information dekhni chahiye.

Auth library ke supported tables use karenge; gym-specific records Aiven PostgreSQL mein unse link honge. Passwords aur activation secrets logs mein nahi likhenge.
Implementation ka order yeh rahega:
1. Auth tables + initial owner setup.
2. Login, session validation aur logout.
3. Backend permission checks.
4. Staff invitation aur activation.
5. Member account linking aur activation.
6. Password reset, suspension aur session revocation.
7. Verify: receptionist owner actions na kar sake, trainer unassigned members na dekh sake, aur member kisi doosre member ka record access na kar sake.

Expenses alag section mein rahenge. Net collection ko profit nahi kahenge—rent, salaries aur doosre expenses abhi subtract nahi hue.
2. Cash payment se collection update hone ka flow
Member cash de → receptionist member/invoice select kare → amount enter kare → confirm → receipt → dashboard update.
Example: Ahmed ki invoice Rs. 3,000 ki hai, woh Rs. 2,000 cash deta hai.
1. Receptionist Ahmed ka profile open karega.
2. Outstanding invoice select karega.
3. “Record Payment” click karega.
4. Rs. 2,000, method Cash, aur actual payment date enter karega.
5. Confirmation screen par member, amount aur invoice check karega.
6. Backend payment aur invoice allocation ek database transaction mein save karega.
7. Unique receipt generate hogi.
8. Ahmed ke dues Rs. 1,000 reh jayenge.
9. Cash collection Rs. 2,000 badhegi.
Partial payment mein sirf received amount collection mein aayega, poori invoice amount nahi.
3. Bank/account transfer ka flow
Transfer do tareeqon se record ho sakega:
Situation        Flow
Member app se proof bheje        Proof submit → pending → staff account mein paisa check kare → approve/reject
Member reception par transfer kare        Staff account mein receipt verify kare → direct confirmed payment record kare




Member ka proof submit hote hi:
- Pending list mein entry aayegi.
- Invoice ke dues unchanged rahenge.
- Collection unchanged rahegi.
- Confirmed receipt issue nahi hogi.
Staff actual transfer verify karega, phir “Confirm Payment” karega. Tab payment save, dues update aur receipt issue hogi.
Reject karne par reason save hoga aur member ko dikhega. Sirf screenshot dekh kar automatic payment confirm nahi karenge.

7. Duplicate payment kaise prevent hogi?
Double-click, slow internet ya retry se collection double nahi honi chahiye.
Problem        Backend handling
Same submit request dobara aaye        Same request key par existing payment return; nayi entry nahi
Do staff same pending transfer approve karein        Sirf ek confirmation successful
Same transfer reference dobara enter ho        Receiving account ke saath duplicate check
Do payments ek invoice par simultaneously aayein        Transaction/locking se remaining balance safely check




Har valid payment ki unique identity hogi. Ek payment multiple invoices mein allocate ho toh collection mein woh payment ek baar count hogi.
8. Galat entry aur refund ka flow
Dono situations separate rahengi:
Situation        Action        Collection par effect
Rs. 2,000 receive hue, Rs. 20,000 enter ho gaye        Owner reason ke saath entry reverse kare → correct Rs. 2,000 entry        Original period ka incorrect collection correct hoga
Valid payment ka Rs. 1,000 member ko wapas diya        Owner refund record kare        Refund date ki net collection Rs. 1,000 kam hogi
Pending transfer reject hua        Rejection reason        Collection par koi effect nahi




Original entry permanently delete nahi hogi. Correction aur refund original payment se linked rahenge.
Refund ke waqt invoice/dues ka treatment bhi explicitly select hoga: fee obligation cancel hui hai ya paisa wapas dene ke bawajood fee due hai? System isko silently decide nahi karega.
9. Receptionist aur owner kya dekhenge?
Role        Collection access

Receptionist        Payment entries, receipts aur apni daily collection summary; gym-wide financial report default nahi
Trainer        Collection access nahi
Member        Sirf apni payments aur receipts




Har access backend permissions se enforce hoga.
10. Day-end cash checking
Receptionist apni shift ke end par “Close Cash Session” open karega:
1. System shift ki expected cash collection dikhayega.
2. Receptionist actual counted cash enter karega.
3. Difference ho toh reason likhega.
4. Owner review karega.
5. Cash handover record save hoga.
Example: expected Rs. 12,000, counted Rs. 11,500 → Rs. 500 shortage flag hogi. Collection records ko shortage cover karne ke liye change nahi karenge.
Opening cash, cash refunds, cash expenses aur owner ko handover drawer balance mein separately track honge. Cash collection aur drawer mein maujood cash alag totals hain.

Dashboard backend confirmed valid payments ka total calculate karega. Frontend manually total add karke permanent balance maintain nahi karega.
Payment save hone ke baad dashboard refresh hoga. Email ya receipt delivery fail ho toh saved payment valid rahegi, delivery retry hogi.
